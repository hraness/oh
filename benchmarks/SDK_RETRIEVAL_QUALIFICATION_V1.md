# Production SDK retrieval qualification

This development study tests the actual default `Oh.search` route with its
local reranker configured. It closes a specific gap in the earlier CloneMem
result: that experiment reranked plain trace text, while the product reranks
`recordDocument` text containing the record key, kind and canonical value.
It does not establish state-of-the-art performance or superiority to an
external memory framework.

## Fixed scope and inputs

Use all **146 questions** from the same two previously exposed development
personas: 114 and 32 questions. Select no questions by answer quality. Reuse
the pinned original trace contents, query stems, question dates and native
QMD semantic captures. Authenticate each captured hit against the source
record digest and the complete eligible trace set.

The native input contains only source memories, question stems, dates and
authenticated semantic rankings. Choice options, correct option IDs, evidence
labels and previous reader responses are absent. The separate scorer is read
only after all native rankings are durable and the native model has closed.

Each persona has a new in-memory Oh SQLite store. Questions run in ascending
date and ID order. Only traces whose source date is at or before the question
date enter the store, before any candidate limit. The same authoritative
store serves every arm for a question.

## Three captured production routes

| Arm | SDK call | Interpretation |
| --- | --- | --- |
| `sdk-semantic` | `oh.search(query, { mode: "semantic", limit: 10 })` | Matched semantic control |
| `sdk-hybrid` | `oh.search(query, { mode: "hybrid", limit: 10 })` | Existing unmodified-query lexical/semantic control |
| `sdk-default-rerank` | `oh.search(query, { limit: 10 })` with both backends configured | Actual default candidate |

Semantic rankings are replayed from authenticated original QMD inference for
the unchanged question stem. They are never invented or regenerated by a
fake model. Every candidate reranker call is fresh local inference through
`OhQmdRerankBackendV1`, with exact SDK `recordDocument` bytes and the pinned
Qwen3-Reranker-0.6B Q8_0 model. The recorder checks every document against its
current record before forwarding the original bytes to that backend.

The default candidate normalizes the lexical query; ordinary hybrid uses the
unmodified query. Therefore **hybrid is not a same-pool reranker ablation**.
This study measures the complete production route, including that difference.

All arms return at most ten complete original traces in rank order through
the unchanged CloneMem reader renderer. The 96 KiB reader-context ceiling is
an admission limit; no source text is truncated. Reranker pools contain at
most sixty documents. The production backend must admit the complete
query/document pairs within its 4,096-token context before scoring each pool.
Any fallback diagnostic, missing score, overflow or native error fails capture;
it cannot silently become a lexical result or an omitted question.

## Native capture and measurements

Freeze source closure, protocol, inputs, QMD package and implementation, model
digest, Bun executable and relevant environment before capture. Bind QMD's
actual SDK import path, the isolated runtime lockfile, node-llama-cpp 3.18.1
and its Metal native package and binary digests. Reconstruct the input
projection from pinned historical captures during freeze and admission.
Use QMD 2.5.3,
the existing model digest `22c9979ce4fbcdc5acdc310c6641c32797eff1aa980b8f7a2db8a8ea23429a48`,
and explicit `QMD_LLAMA_GPU=metal`, `QMD_RERANK_CONTEXT_SIZE=4096`,
`QMD_EMBED_PARALLELISM=1`, `GGML_METAL_NO_RESIDENCY=1` on the selected Mac host.
The root owns native scheduling, the child process, its output and collection.

Capture exactly 146 queries with one shared model, immutable per-query intent
and result files, and a **3,600-second** native budget. An occupied incomplete
capture is preserved and cannot resume or overwrite its first scores. Native
failure requires a new reviewed protocol decision; it never triggers automatic
model downloads, retries, parameter changes or paid calls.

Report complete/failed query counts, candidate-pair count, maximum pool and
document bytes, context sizes, first-query duration, all-query p50/p95 and warm
p50/p95 after the first query. Timings measure the reranker backend and SDK
route on this host. They exclude the historical semantic inference cost and
cannot be presented as total live retrieval latency. The native screen must
complete all 146 queries, close every owned resource and keep warm reranker
p95 at or below **30 seconds** before reader calls.

## Reader comparisons and fixed decision

The existing paired-reader framework admits two arms. Preserve that boundary:

1. **Primary:** `sdk-default-rerank` versus `sdk-semantic`, all 146 questions,
   three separate reader attempts per arm: 876 logical cases.
2. **Secondary:** `sdk-default-rerank` versus `sdk-hybrid`, the same population
   and repeats in a separately frozen campaign: another 876 logical cases.

The secondary campaign is optional only for budget or execution constraints;
whether to launch it must be fixed before primary answer scores are opened.
Its candidate attempts are fresh responses, not shared primary responses.
Neither comparison chooses questions or policies from observed answers.

Use the unchanged native multiple-choice prompt, Gateway
`openai/gpt-4o-mini`, temperature 0.1, output limit 512, and exact option-ID
scoring. No judge. Record actual provider identity; an alias is not an
immutable snapshot.

The primary development gate requires every condition:

- All 876 logical cases complete, with no failed, refused, truncated,
  unresolved or unattempted response.
- Mean candidate answer accuracy improves by at least **3 percentage
  points**, with nonnegative deltas in both personas.
- Recall@10 improves overall, with nonnegative deltas in both personas.
- Complete native capture, no fallback, unchanged frozen inputs, and the
  stated latency/cleanup conditions.

Report any weaker result as failing this development gate. The secondary
comparison is descriptive and cannot rescue a failed primary gate. Report
per-persona and overall counts, differences, context sizes, costs and errors.
Two exposed personas do not support a pristine-holdout or broad population
claim, irrespective of the gate outcome.

## Failure and spending policy

The user authorized an additional **$25 maximum**, separate from the recorded
**$12.876502** of earlier task exposure. Both comparisons together may use at
most 1,752 physical reader calls. Deduplication can lower actual physical
calls, never the logical matrix. Each campaign has a cap of at most $12.50;
the exact full reservation must fit its cap before any call. Parent accounting
must bind all previous exposure and the shared $25 additional ceiling.

The root is the sole provider owner. Before any answer scores are opened,
freeze the selected campaign set and cumulative task allowance in the
independently reviewed launch packet; individual campaign caps alone do not
prove that shared accounting boundary. No command in this qualification runner
dispatches paid requests. Use the existing reviewed paired-memory runner,
selected project OIDC authority and immutable native ledger after independent
launch review and a clean committed checkpoint.

Terminal provider failures remain captured and charged according to the native
ledger. They count as failures and zero accuracy in the primary intention-to-
run summary; incomplete execution fails the gate. No replacement complete
campaign may silently replace the primary matrix. Preserve all receipts and
report any later recovery as a separately amended study.

## Commands

All output directories are new private locations. `ORIGINAL_ROOT` is the
preserved checkout containing the pinned historical captures; no command
modifies those files.

```sh
bun scripts/benchmarks/sdk-retrieval-qualification-run.ts prepare ORIGINAL_ROOT NEW_DIRECTORY
bun scripts/benchmarks/sdk-retrieval-qualification-run.ts freeze NEW_DIRECTORY MODEL_PATH QMD_PACKAGE_PATH
```

After the root reviews the freeze and admits the native process through the
host scheduler, run with the explicit environment above:

```sh
bun scripts/benchmarks/sdk-retrieval-qualification-run.ts capture NEW_DIRECTORY FREEZE_SHA
```

Only after complete native capture and closure, the root records
`native-owner.json` with protocol `oh.sdk-retrieval-native-owner.v1`, the exact
`freezePin` and `capturePin`, `exitCode: 0`, `nativeCleanupWarnings: 0`,
`nativeErrors: 0`, `ownedChildCollected: true`, `deadlineSeconds: 3600`, and
SHA-256s of captured stdout and stderr. The root must actually enforce the
child deadline and inspect the native logs; a resolved SDK close alone cannot
attest to native process cleanup. `OWNER_SHA` is the digest of this receipt.

Prepare each selected paid comparison with its separately reconciled campaign:

```sh
bun scripts/benchmarks/sdk-retrieval-qualification-run.ts prepare-paid NEW_DIRECTORY FREEZE_SHA CAPTURE_SHA OWNER_SHA semantic CAMPAIGN_JSON NEW_PREPARED_DIRECTORY
bun scripts/benchmarks/sdk-retrieval-qualification-run.ts prepare-paid NEW_DIRECTORY FREEZE_SHA CAPTURE_SHA OWNER_SHA hybrid CAMPAIGN_JSON NEW_PREPARED_DIRECTORY
```

Preparation authenticates the owner's capture digest, every immutable query
checkpoint, reranker score coverage, SDK replay of the same captured scores,
source rendering and recomputed latency gate before admitting the paid plan.
The preparation receipt reports exact reservation and call bounds. It does
not authorize launch. Public reports contain aggregate measurements and pins;
source text, questions, answers, gold keys and local paths remain private.
